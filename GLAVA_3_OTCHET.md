# ГЛАВА 3. ПРАКТИЧЕСКАЯ РЕАЛИЗАЦИЯ СИСТЕМЫ

*Информационная система «Future Greenhouse» — управление тепличным хозяйством*

---

В третьей главе описывается, как разработанное веб-приложение было реализовано на практике: какие модули входят в состав системы, как устроены серверные API, интерфейс пользователя и подключение физического датчика ESP32. Материал изложен в связи с выбранным стеком технологий: **Next.js 16**, **TypeScript**, **PostgreSQL** (в том числе размещение на **Supabase**), **Tailwind CSS**, развёртывание на **Vercel**, интеграция **OpenAI API** (модели **gpt-4o-mini** и **gpt-4o** для анализа изображений), а также аппаратная часть **ESP32 + DHT22**.

## 3.1 Реализация модулей аутентификации и мониторинга

Модули первой группы обеспечивают безопасный вход в систему, разграничение прав по ролям и работу с показаниями микроклимата в теплицах. Без надёжной авторизации невозможно отделить действия администратора от действий оператора теплицы; без мониторинга датчиков теряется смысл автоматизации учёта температуры и влажности.

### 3.1.1 Реализация модуля авторизации

Модуль авторизации нужен, чтобы только зарегистрированные сотрудники получали доступ к данным хозяйства, а права на изменение информации соответствовали должностным обязанностям.

**Страница входа.** Пользователь открывает маршрут `/login`. На клиенте отображается форма с полями «логин» и «пароль» (компонент страницы в каталоге `src/app/login/`). Перед отправкой данные проверяются с помощью библиотеки **Zod** на стороне сервера; на клиенте дополнительно блокируется отправка пустой формы. После нажатия кнопки «Войти» выполняется `fetch` на `/api/auth/login` с телом `{ login, password }` в формате JSON. При успехе браузер получает ответ `200` и cookie, после чего выполняется переход на главную (`/`) или на адрес из параметра `from`, если пользователь был перенаправлен middleware.

При ошибке сервер возвращает сообщение «Неверный логин или пароль», и оно показывается пользователю без раскрытия, существует ли такой логин в базе — это снижает риск подбора учётных записей. Отдельно обрабатывается ситуация, когда учётная запись деактивирована (`is_active = 0`): вход для неё также запрещён с тем же общим текстом ошибки.

Для демонстрации на защите диплома подготовлены учётные записи команды (создаются сидом и кнопкой «Создать аккаунты команды» в разделе `/users`): агроном `aigul`, операторы `ruslan` и `sofia`, директор `madina`, администратор `admin`. Пароли задаются по шаблону «логин + 123», например `admin123`. Это удобно при ручном тестировании ролей, как показано на рисунке 3.2.

**Обработчик POST `/api/auth/login`.** Последовательность работы следующая:

1. Тело запроса разбирается и валидируется схемой Zod.
2. В таблице `users` выполняется поиск записи по полю `login` с условием `is_active = 1`.
3. Введённый пароль сравнивается с полем `password_hash` через **bcrypt.compareSync** (библиотека **bcryptjs**).
4. При успехе формируется JWT-токен функцией `signAuthToken` из модуля `src/lib/auth.ts`.
5. Токен записывается в **httpOnly**-cookie с именем **`fg_token`** — JavaScript на странице не может прочитать cookie, что защищает от простой кражи токена через XSS.
6. В ответ клиенту возвращается `{ ok: true }`, после чего выполняется переход на главную страницу.

**Состав JWT.** В полезной нагрузке токена (алгоритм **HS256**, библиотека **jose**) хранятся:

- `sub` — идентификатор пользователя;
- `login` — логин;
- `role` — роль (`admin`, `director`, `agronomist`, `worker`);
- `fullName` — ФИО для отображения в интерфейсе;
- стандартные поля `iat` и `exp` (срок действия задаётся переменной окружения, например `7d`).

Связь пользователя с записью в таблице `employees` хранится в БД (`users.employee_id`), а не внутри JWT — при необходимости она подгружается отдельным запросом.

**Cookie и срок жизни токена.** Функция `attachAuthCookie` из `src/lib/auth.ts` устанавливает cookie `fg_token` с флагами **httpOnly**, **sameSite=lax** и путём `/`. В production дополнительно включается **secure**. Срок действия согласован с полем `exp` внутри JWT (переменная окружения `AUTH_TOKEN_TTL`, по умолчанию несколько суток). При выходе (`POST /api/auth/logout`) cookie очищается.

**Middleware.** Файл `middleware.ts` в корне проекта перехватывает запросы к защищённым страницам. Если cookie `fg_token` отсутствует или подпись токена недействительна, пользователь перенаправляется на `/login` с параметром `from` (адрес, куда он хотел попасть). Для отдельных разделов заданы правила: например, `/users` и `/db` доступны только роли `admin`, `/sensor-entry` — `admin` и `worker`, `/reports` и `/cultures` — `admin`, `agronomist`, `director`. При несоответствии роли показывается страница `/403`.

Исключение сделано для **IoT-устройств**: POST на `/api/sensors` с заголовком `x-iot-key` проходит middleware без cookie — иначе ESP32 не смог бы отправлять данные.

**Второй рубеж — `requireApiRoles()`.** Даже если пользователь обратится к API напрямую, каждый маршрут в `src/app/api/**/route.ts` вызывает функцию `requireApiRoles` из `src/lib/api/rbac.ts`. Она читает сессию из cookie и проверяет, входит ли роль в разрешённый список. Пример: создание теплицы разрешено `admin` и `agronomist`, удаление — только `admin`.

**Профиль и смена пароля.** На странице `/profile` пользователь может изменить ФИО и пароль. Смена пароля идёт через **PUT `/api/profile/password`**: сначала проверяется текущий пароль через `bcrypt.compare`, затем новый хеш сохраняется в `users.password_hash`.

**Журналирование.** При успешном входе:

- обновляется поле `users.last_login`;
- в таблицу `login_history` добавляется запись с IP и User-Agent (если таблица создана миграциями);
- в `action_logs` фиксируется действие `login` с описанием «Вход в систему».

Аналогично при изменении данных в других модулях вызывается функция `auditLog`, которая пишет в `action_logs` кто, что и когда изменил.

**Роли и навигация.** В системе четыре роли:

| Роль | Назначение в проекте | Основные разделы меню |
|------|-------------------|------------------------|
| `admin` | Полный доступ, настройка пользователей и БД | Все пункты, включая «Пользователи» и «База данных» |
| `director` | Просмотр сводок и отчётов | Дашборд, теплицы, культуры, параметры, отчёты, ИИ |
| `agronomist` | Планирование: культуры, полив, задачи | То же + редактирование без админ-разделов |
| `worker` | Оператор теплицы: свои задачи, ввод датчиков | Дашборд, параметры, полив, задачи, ручной ввод, уведомления |

Пункт «ИИ-ассистент» в меню доступен `admin`, `agronomist`, `director`; оператор (`worker`) работает с практическими разделами на месте.

### 3.1.2 Реализация модуля управления теплицами

Модуль теплиц — центральный справочник: к каждой теплице привязаны нормы температуры и влажности, статус, ответственный сотрудник и список выращиваемых культур.

**API GET `/api/greenhouses`.** Данные для списка карточек формирует функция `listGreenhousesWithStatus()` в `src/lib/repo/greenhouses.ts`. Запрос построен на двух CTE (общих табличных выражениях):

1. **`last_sensor`** — `SELECT DISTINCT ON (greenhouse_id) ... FROM sensor_data ORDER BY greenhouse_id, recorded_at DESC`. Так PostgreSQL для каждой теплицы оставляет одну строку — с самой свежей датой измерения. Это эффективнее, чем выполнять подзапрос «последняя температура» для каждой карточки отдельно.

2. **`next_w`** — ближайший по времени полив из `watering_schedule`, у которого `is_done = 0`, снова через `DISTINCT ON (greenhouse_id)`.

Основная выборка соединяет таблицы `greenhouses`, `employees` (ФИО ответственного), `last_sensor` и `next_w`. Список культур формируется подзапросом `string_agg(c.name, '||')` с фильтром: исключаются записи с пометками `demo`, `demo-rich` и имена вида `Демо-%`, чтобы в интерфейсе не отображались учебные заглушки.

На клиенте (`src/app/(app)/greenhouses/page.tsx`) для каждой карточки вычисляется цвет статуса и подсветка температуры/влажности: если значение меньше `temp_min` или больше `temp_max`, поле температуры подсвечивается как отклонение; аналогично для влажности. Количество открытых задач по теплице может выводиться на дашборде через отдельный KPI-запрос; в карточке теплицы акцент сделан на микроклимате и ближайшем поливе.

**Интерфейс `/greenhouses`.** На странице теплицы выводятся карточками (адаптивная сетка). На карточке отображаются:

- название и тип (стеклянная / поликарбонатная / плёночная);
- статус: активна, обслуживание, отключена (цветовая индикация);
- последние T° и влажность — с подсветкой, если значение выходит за `temp_min`–`temp_max` или `humidity_min`–`humidity_max`;
- перечень культур в теплице;
- ответственный сотрудник из таблицы `employees`.

Отдельной страницы `/greenhouses/[id]` в текущей версии нет: вся информация по теплице доступна в общем списке и в связанных разделах (параметры, культуры, задачи).

**Создание и редактирование.** Форма в модальном окне содержит поля:

- `name` — название;
- `type` — тип теплицы;
- `area` — площадь, м²;
- `temp_min`, `temp_max`, `humidity_min`, `humidity_max` — нормативы;
- `status` — статус эксплуатации;
- `responsible_employee_id` — ответственный оператор.

Права на операции:

- **POST** (создание) — `admin`, `agronomist`;
- **PUT** (изменение) — `admin`, `agronomist`;
- **DELETE** — только `admin`.

После каждой операции вызывается `auditLog` с указанием сущности `greenhouses` и текстом изменения.

### 3.1.3 Реализация модуля мониторинга датчиков

Мониторинг нужен, чтобы агроном видел динамику климата, а при отклонении от норм система могла сформировать уведомление. Данные поступают тремя путями: с физического датчика ESP32, с программной симуляции (для тестов) и с ручного ввода оператором.

**Ручной ввод — `/sensor-entry`.** Оператор (`worker`) или администратор выбирает теплицу и вводит температуру, влажность и CO₂. Запрос уходит на **POST `/api/sensors`** с JWT-авторизацией. Сервер валидирует поля через Zod-схему `PostSchema` (положительный `greenhouse_id`, числовые T° и влажность; CO₂ можно передать как `co2` или `co2_level`).

Общая логика записи вынесена в функцию **`persistSensorReading`** в том же файле маршрута. Она выполняет **транзакцию**:

- `INSERT` в `sensor_data`;
- при ручном вводе — запись в `action_logs` через `auditLog`;
- сравнение с нормами из `greenhouses`;
- при отклонении — `INSERT` в `notifications` с типом **`тревога`** (температура) или **`предупреждение`** (влажность).

Таким образом, одно действие пользователя или устройства атомарно отражается и в истории измерений, и в системе оповещений.

**Уведомления при отклонении.** Если температура или влажность вне диапазона, в таблицу `notifications` добавляется запись:

- тип **`тревога`** — при критическом отклонении температуры;
- тип **`предупреждение`** — при отклонении влажности (логика задана в коде маршрута).

Текст сообщения содержит название теплицы и фактические значения.

**Подключение ESP32 + DHT22.** Для дипломной демонстрации собран стенд: микроконтроллер **ESP32**, датчик **DHT22** (температура и влажность), соединительные провода и блок питания. Прошивка разработана в **Arduino IDE**:

1. Подключение к Wi‑Fi сети предприятия (или учебной лаборатории).
2. Чтение DHT22 каждые несколько секунд.
3. Формирование JSON и отправка **HTTP POST** на адрес сервера разработки (например `http://IP_компьютера:3000/api/sensors`).

**Формат JSON от устройства:**

```json
{
  "greenhouse_id": 1,
  "temperature": 23.4,
  "humidity": 61.0,
  "co2_level": null
}
```

**IoT-аутентификация.** В заголовке запроса передаётся **`x-iot-key`** со значением из переменной окружения **`IOT_SECRET`** (в файле `.env.local`, например `greenhouse_iot_key_2024`). В начале POST-обработчика `/api/sensors` проверяется: если заголовок есть и совпадает с секретом — JWT не требуется; иначе выполняется обычная проверка ролей `admin` / `worker`. Так разделены «человек в браузере» и «устройство в сети».

Если `co2_level` равен `null` (отдельного датчика CO₂ на стенде нет), в базу записывается значение **650 ppm** по умолчанию.

**Чтение истории — GET `/api/sensors`.** Клиент передаёт `greenhouse_id`, а также `range=day` или `range=7d`. Сервер возвращает массив точек для построения графика. Параметр `recent=1` используется для быстрого получения последнего значения (панель ESP32 на `/db`). Доступ разрешён любой авторизованной роли (`requireApiRoles("any")`), но данные по смыслу используются в разделах мониторинга.

**Страница «Параметры» — `/parameters`.** Здесь отображаются:

- карточки всех теплиц с текущими показаниями и индикаторами нормы;
- **линейные графики Chart.js** по истории за день или 7 дней (температура, влажность, CO₂);
- блок предупреждений при выходе за нормы.

Данные запрашиваются через **GET `/api/sensors`** с параметрами `greenhouse_id` и `range`. На клиенте настроено **автообновление каждые 3 секунды** (`setInterval(..., 3000)`), поэтому после прихода новой записи от ESP32 график обновляется без перезагрузки страницы.

**Панель ESP32 в разделе «База данных».** Для администратора на странице `/db` вверху выведена компактная панель «ESP32 · теплица №1»: крупно температура и влажность по последней записи из БД для первой теплицы, обновление также раз в 3 секунды. Ниже сохранены админ-функции: симуляция датчиков и просмотр таблиц PostgreSQL.

**Программная симуляция.** В том же разделе `/db` администратор может включить **«Симуляцию данных датчиков»**. Серверный модуль `src/lib/sensor-simulation.ts` каждые **5 секунд** (`TICK_MS = 5000`) генерирует правдоподобные значения по **всем** теплицам (синусоида в пределах норм карточки) и пишет их в `sensor_data`. Это удобно для отладки без физического датчика. Важно не путать интервалы: **ESP32 шлёт ~3 с**, **экран обновляется 3 с**, **симуляция в БД — 5 с**.

## 3.2 Реализация модулей управления производственными процессами

Вторая группа модулей покрывает ежедневную работу хозяйства: полив, задачи персонала и отчёты для руководства.

### 3.2.1 Реализация модуля планирования и контроля полива

Полив нужно планировать заранее и фиксировать факт выполнения, иначе сложно анализировать расход воды и соблюдение графика.

**Создание записи.** Агроном или администратор заполняет форму:

- `greenhouse_id` — теплица;
- `watering_type` — тип (в проекте используются текстовые значения, например «капельный»);
- `scheduled_at` — дата и время;
- `duration_minutes` — длительность, мин;
- `volume_liters` — объём, литры;
- `notes` — примечание (необязательно).

Данные отправляются на **POST `/api/watering`**.

**Получение расписания.** **GET `/api/watering`** принимает параметр `range`:

- `today` — поливы на сегодня;
- `week` — на ближайшую неделю.

Оператор (`worker`) видит только поливы **своей** теплицы (фильтр по `greenhouse_id` из связи `users.employee_id` → `employees.greenhouse_id`).

**Отметка выполнения.** Оператор отмечает полив выполненным через **PUT `/api/watering`**: передаётся только `id` и `is_done = 1`. В коде для роли `worker` явно запрещено передавать другие поля — иначе возвращается `403 Forbidden`. Обновление выполняется с условием `greenhouse_id = теплица оператора`, чтобы нельзя было отметить чужой полив. Факт действия фиксируется в **`action_logs`** (кто отметил и какой идентификатор записи), а не в отдельных полях `done_by` в таблице полива. Агроном и администратор при PUT могут менять полный набор полей расписания.

**Отображение.** В интерфейсе `/watering` записи разделены визуально: запланированные и выполненные; используется цветовая индикация статуса. В отчётах по поливу агрегируется `SUM(volume_liters)` и доля выполненных событий.

### 3.2.2 Реализация модуля управления задачами персонала

Задачи связывают агронома и операторов: кто, что и к какому сроку должен сделать в теплице.

**Структура задачи** (таблица `tasks`):

- `title`, `description` — суть поручения;
- `priority` — приоритет: **`обычный`**, **`высокий`**, **`срочный`**;
- `deadline` — срок;
- `greenhouse_id` — теплица (может быть пустым);
- `assigned_to` — ссылка на `employees.id`;
- `is_completed` — флаг выполнения.

**Фильтрация по роли.** При **GET `/api/tasks`** для роли `worker` в SQL добавляется условие `assigned_to = employee_id` текущего пользователя. Оператор не видит чужие задачи. Агроном и администратор получают полный список с сортировкой: сначала невыполненные, по сроку.

**Просроченные задачи.** В интерфейсе задача считается просроченной, если `is_completed = 0` и `deadline` меньше текущего времени — для таких строк применяется красная метка.

**Выполнение.** Оператор нажимает «Отметить выполненной»; отправляется **PUT `/api/tasks`** с `is_completed: 1`. Сервер проверяет, что задача назначена именно этому сотруднику (для роли `worker`).

**Уведомления.** При создании или переназначении задачи вызывается функция `notifyEmployeeTask`: в `notifications` создаётся запись с полем **`target_user_id`** — уведомление видит только назначенный оператор (и администратор при просмотре всех).

### 3.2.3 Реализация модуля формирования отчётности

Отчётность нужна директору и агроному для анализа работы за период без ручного сбора таблиц в Excel.

**API.** **GET `/api/reports`** принимает query-параметры:

- `period` — `day` | `week` | `month` | `year` (интервал относительно текущего момента в UTC);
- `format` — `json` | `pdf` | `excel`.

В режиме **JSON** функция `buildReport` собирает:

- суммарный объём полива `SUM(volume_liters)` из `watering_schedule` за интервал;
- долю выполненных задач (`is_completed = 1` к общему числу) из `tasks`;
- показатели урожая/культур (по данным таблицы `cultures` и связанным полям);
- временной ряд для графиков на странице;
- таблицу агрегатов по теплицам.

Маршрут помечен `export const runtime = "nodejs"`, потому что генерация PDF через **PDFKit** и Excel через **ExcelJS** требует Node.js API, недоступных на Edge-runtime.

**PDF.** Экспорт реализован через библиотеку **PDFKit**. Для корректного отображения кириллицы подключён шрифт **DejaVu Sans** из каталога `public/fonts/DejaVuSans.ttf`. Документ содержит заголовок, KPI-блок и таблицу показателей.

**Excel.** Экспорт через **ExcelJS**: несколько листов («Сводка», «По теплицам», данные для графика). На лист может вставляться PNG-график, сформированный через сервис **quickchart.io** по параметрам отчёта. Ячейки оформляются (жирный шрифт заголовков, границы).

**Интерфейс `/reports`.** На странице пользователь выбирает период, смотрит интерактивные графики **Chart.js** и нажимает кнопку выгрузки PDF или Excel без полной перезагрузки страницы (скачивание файла через API).

### 3.3.1 Реализация модуля AI-ассистента

ИИ-модуль помогает быстрее интерпретировать накопленные данные и получить текстовые рекомендации без отдельного чат-бота в мессенджере.

Раздел доступен по маршруту **`/ai`** для ролей `admin`, `agronomist`, `director`. Интерфейс разбит на **вкладки**:

1. **Чат** — диалог с моделью **gpt-4o-mini**; в запрос подмешивается контекст из БД (теплицы, последние датчики, открытые задачи, поливы).
2. **Карта теплиц** — схема блоков; цвет отражает оценку «здоровья» теплицы (датчики, задачи, полив); по клику — краткая AI-сводка.
3. **Прогноз** — построение тренда на несколько дней по истории `sensor_data` за 7 суток и отметка зон риска относительно норм.
4. **Детектор аномалий** — статистический разбор без OpenAI: поиск выбросов и резких скачков на графике за 7/14 дней.
5. **Советы** — автоматические рекомендации по правилам и через модель при открытии вкладки.
6. **Анализ фото** — загрузка снимка растения или плода; модель **gpt-4o** (Vision) возвращает описание состояния и рекомендации.
7. **Планировщик недели** — черновик плана задач и поливов на 7 дней с возможностью сохранить в системе.
8. **Обучение** — интерактивная инструкция для новых сотрудников: выбор роли «агроном» или «оператор», шаги по разделам меню.

История чата хранится в таблице **`ai_chat_history`** (последние сообщения подгружаются при новом вопросе).

**Системный контекст для модели.** Перед вызовом OpenAI серверные обработчики в `src/app/api/ai/` и вспомогательные модули `src/lib/ai/` формируют текстовый блок с актуальным состоянием хозяйства: список теплиц, последние показания (аналогично `DISTINCT ON` по `sensor_data`), открытые задачи и ближайшие поливы. Это позволяет модели отвечать не «в общем», а с привязкой к цифрам из БД. Для вкладки **«Детектор аномалий»** используется отдельный алгоритм в `src/lib/ai/` (статистика по ряду за 7 и 14 суток, поиск выбросов) **без** запроса к OpenAI — график строится на клиенте в `AnomalyDetectorPanel.tsx`.

**Анализ фото.** Пользователь загружает изображение; файл отправляется на API, который вызывает модель **gpt-4o** с поддержкой vision. В ответе выводится описание состояния растения или плода и практические рекомендации. Тексты подсказок в интерфейсе упрощены, чтобы оператору было понятно, что именно анализируется.

**Планировщик недели.** Генерируется черновик расписания задач и поливов на семь дней; пользователь может сохранить предложенные записи в основные таблицы через API (с проверкой ролей).

**Обучение.** Компонент `TrainingTour.tsx` показывает пошаговый тур по разделам меню в зависимости от выбранной роли (агроном или оператор), что снижает порог входа для нового сотрудника.

При отсутствии переменной `OPENAI_API_KEY` вкладки чата, советов, анализа фото и планировщика показывают понятное сообщение об ошибке, тогда как карта, прогноз по формулам и детектор аномалий остаются доступными.

Под каждой вкладкой добавлен текст «как это работает» простым языком — без излишнего технического жаргона, чтобы оператор мог понять смысл подсказки.

Если ключ OpenAI не задан или сервис недоступен, остальные вкладки (карта, аномалии, прогноз по формулам) продолжают работать; недоступным остаётся только то, что напрямую вызывает API OpenAI.

### 3.3.2 Тестирование системы

Тестирование подтверждает, что критичные части системы работают стабильно после изменений в коде.

**Модульные тесты (Vitest).** В каталоге `tests/unit/` размещены файлы:

- **`adapter.test.ts`** — проверка адаптера `DbAdapter`: конвертация плейсхолдеров `?` в `$1`, `$2` для драйвера PostgreSQL, корректная обработка пустых и граничных параметров;
- **`rbac.test.ts`** — проверка, что `requireApiRoles` пропускает разрешённые роли и возвращает ответ с кодом 401/403 для запрещённых.

Тесты JWT в отдельном файле не выделены: корректность токена косвенно проверяется e2e-сценарием входа и middleware при каждом запросе в эксплуатации. При дальнейшем развитии проекта целесообразно добавить unit-тесты на `signAuthToken` / `verifyAuthToken` с подменой секрета.

Запуск: **`npm test`** (скрипт в `package.json` вызывает Vitest).

**Сквозной тест (Playwright).** Файл `tests/e2e/smoke.spec.ts` имитирует сценарий: открыть `/login`, ввести `admin` / `admin123`, убедиться, что открывается дашборд, запрос **GET `/api/kpi`** возвращает статус 200.

Запуск: **`npm run test:e2e`**.

**Ручная проверка** (выполнена при разработке):

- вход под ролями `admin`, `agronomist`, `worker`, `director`;
- ввод показаний выше нормы — появление уведомления;
- отправка данных с ESP32 с заголовком `x-iot-key`;
- генерация PDF и Excel из раздела отчётов;
- проверка вкладок ИИ и панели датчика на `/db`.

### 3.3.3 Экономическая эффективность и перспективы развития

**Экономическая оценка** (ориентировочная, для одного хозяйства на примере теплицы площадью 1000 м²):

| Статья | Расчёт | Эффект, тг/год |
|--------|--------|----------------|
| Экономия времени на отчётах | ~3 ч/нед × 52 нед ≈ 156 ч; при 1500 тг/ч | **≈ 234 000** |

Расчёт по отчётности: 3 часа в неделю × 52 недели = 156 часов в год. При стоимости часа работы специалиста 1500 тенге: 156 × 1500 = **234 000 тг/год**. Раньше агроном вручную собирал таблицы в Excel; теперь кнопка на `/reports` формирует PDF или Excel за несколько секунд.

Расчёт по урожаю (пример для томатов): площадь 1000 м², урожайность 50 кг/м² → 50 000 кг; при цене 250 тг/кг выручка условно 12,5 млн тг за сезон. Своевременное уведомление о перегреве или низкой влажности снижает риск гибели части урожая; даже **10 %** сохранённого объёма дают **1,25 млн тг** — порядок величины существенно выше затрат на ПО.

Оптимизация полива (20 % воды): при годовом объёме полива, эквивалентном 900 000–2 750 000 тг (в пересчёте на воду и электроэнергию насосов), экономия 20 % даёт диапазон **180 000 – 550 000 тг/год**.
| Снижение потерь урожая | Урожай 50 кг/м² × 1000 м² × 250 тг/кг = 12,5 млн тг; предотвращение 10% потерь | **≈ 1 250 000** |
| Экономия воды | ~20% от годового объёма полива (оценка) | **180 000 – 550 000** |
| Затраты на облако | Vercel + Supabase (бесплатные тарифы на этапе пилота) | 0 – низкие |
| OpenAI API | Платные запросы к модели | **~2 000 – 6 000 тг/мес** |
| Оборудование IoT | ESP32 + DHT22 + комплектующие на 1 теплицу | **~58 000** (единовременно) |

Даже без учёта предотвращения потерь урожая окупаемость программной части при пилотном внедрении достигается за счёт сокращения ручного труда на сводках и таблицах.

**Перспективы развития:**

- расширение IoT: протокол **MQTT**, управление реле полива, сеть **LoRaWAN** для удалённых теплиц;
- мобильное приложение или **PWA** с push-уведомлениями;
- режим **multi-tenant** для нескольких хозяйств в одной установке;
- тиражирование как **SaaS** на рынок Казахстана и Центральной Азии;
- дообучение или тонкая настройка модели на локальных агрономических данных.

### 3.4 Краткое резюме реализации (итоги главы)

В ходе практической реализации была создана единая веб-система, объединяющая учёт теплиц, мониторинг климата, планирование полива и задач, отчётность и интеллектуальные подсказки. Архитектура построена по классической схеме «клиент — API — PostgreSQL»: интерфейс на **React** в рамках **Next.js App Router**, бизнес-логика в серверных маршрутах `src/app/api/`, доступ к данным через слой `src/lib/repo/` и прямые подготовленные запросы с адаптером плейсхолдеров.

Безопасность обеспечивается на двух уровнях: **middleware** для страниц и **`requireApiRoles`** для API. IoT-канал вынесен в отдельную схему аутентификации по секретному ключу, что позволило подключить ESP32 без хранения пароля пользователя в прошивке.

Наиболее трудоёмкими оказались модули с визуализацией (Chart.js, автообновление), формированием отчётов (PDF/Excel с кириллицей) и разделом ИИ с несколькими независимыми вкладками. Аппаратная часть (ESP32 + DHT22) подтвердила работоспособность сквозного сценария: измерение → HTTP → база → график в браузере за несколько секунд.

Дальнейшая работа может быть направлена на расширение сенсорики (CO₂, почва), мобильные уведомления и промышленные протоколы (MQTT), что не отменяет ценности уже реализованного ядра системы для учебного и пилотного внедрения на предприятии.
